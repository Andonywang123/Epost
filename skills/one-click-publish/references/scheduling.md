# 时间与排期

## 看板含义

“一键草稿”不是预约保存草稿：确认后尽快保存，时间字段必须为空。切到草稿立即丢弃先前定时时间；再切回发布时重新选择，不带入隐藏旧值。

“一键发布”需要明确选立即或定时。立即发布表示队列轮到该平台时提交；平台审核和处理时间不在总控保证范围内。定时发布表示确认后逐平台建立原生排期，不是等到时刻才开始上传。

## 区域与时区

| 区域 | 具体 IANA 时区 |
| --- | --- |
| 中国区 | `Asia/Shanghai` |
| 美区 | `America/Los_Angeles`、`America/New_York`、`America/Chicago` |
| 英欧区 | `Europe/London`、`Europe/Paris`、`Europe/Berlin` |
| 澳区 | `Australia/Sydney`、`Australia/Perth`、`Australia/Brisbane` |
| 本地时间 | 宿主确认的用户本地 IANA 时区 |

不要把服务器时区当成用户时区，也不要把“美区”默认成统一 UTC 偏移。首次选择多时区区域时让用户显式选城市。UI 可从 `Intl.DateTimeFormat().resolvedOptions().timeZone` 提出本地值，但宿主应将其绑定到会话；服务端不能信任任意客户端伪造的本地区域。

国内平台不显示境外区域选项，显示 `Asia/Shanghai`。境外平台即使选择中国区，也不改变平台受众、语言、账号地区或 API 的地域标签；这些是不同字段。

## 滑杆

日期 + `0..1439` 的分钟滑杆（步长 1，`00:00..23:59`）+ 同步的精确时间输入。拖动只改当前平台的本地墙上时间，不连带更改其他平台。日期、时间、时区共同确定一个时刻；仅滑杆分钟值不足以执行排期。

最终计划保存 `date`、`minute`、`timezone`、实际 UTC 偏移、带时区的 `scheduledAt` 与对应 UTC 时刻。确认框显示完整年月日、时分、时区和 UTC 偏移，避免跨日误读。

## 夏令时与过期

使用宿主 IANA 数据或 Python `zoneinfo` 解析，不写死偏移：

- 春季跳时导致不存在的时刻：报错并要求改时间，不自动顺延。
- 秋季重复时刻：让用户从两次发生的 UTC 偏移中明确选择，使用 `fold=0|1` 记录。
- 过去的时间、平台要求的最短提前量不足：阻止提交。
- 排队或转换耗时后再次检查提前量；已过期的定时任务必须暂停重选，不改成立即发布。

当前小红书适配器有 60 分钟最短提前量。YouTube 适配器要求未来时间并以私密状态创建预约公开的视频。宿主应将实际适配器限制放入能力记录；未知的最大排期范围不得虚构。

调度时将同一绝对时刻分别映射为小红书 `schedule_at`、YouTube `publish_at`。转换时不能丢失时区。草稿/立即发布时两个字段都为空，避免残留定时值。
